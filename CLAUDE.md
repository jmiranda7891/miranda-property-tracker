## What this is
A private estate-planning web app listing the Miranda family's ~40 real estate properties across Mexico and the Chicago area — unified list (cards or a sortable Excel-like table), Google Maps links, one-time AI-researched area context + value-estimate commentary per property, an EN/ES toggle, a Google Sheet export, and an in-app admin panel for managing who can access it. Built for Jorge (jorge@orderexpress.com) as a personal/family tool — not a client product, not related to the sibling `clpr-social-media` (CL Social Media App) repo, though it deliberately reuses that repo's proven Apps Script patterns.

## Architecture
- Apps Script web app: `doGet` → HtmlService. Client↔server ONLY via `google.script.run` (async).
- Files: `Code.js` (server), `Index.html` (shell), `Styles.html`, `JavaScript.html` (client app). Assembled with `include()`. Exactly these 5 files (+`appsscript.json`) are ever pushed — `.claspignore` is a whitelist, not a blocklist.
- Data: **one spreadsheet total** — "Miranda Family - Property Registry" — created lazily by `ensureRegistry_()` the first time anyone opens the app, ID stored in Script Properties (`REGISTRY_ID`), never hardcoded. This is a SINGLE-TENANT app (one family, one property list), unlike the sibling CL app's per-client-spreadsheet pattern — there is no "Clients" tab or provisioning flow here.
  - `Properties` tab (schema v2 — see below): `countryCode`, `paisRaw`, `tipo`, `referencia`, `propietario` (shown as **"Dueño Beneficiario"**), `direccion`, `direccion2` (apt/interior/suite number, added v1.7 — see "direccion2 + the Union St regex bug" below), `ciudad`, `estado`, `cp`, `lotSizeValue`/`lotSizeUnit`, `constructionSizeValue`/`constructionSizeUnit` (added v1.8), `observacionesRaw`, `status` (4 values), `precioEstimadoUSD`, `precioEstimadoIsPlaceholder`, `acquisitionDate`/`acquisitionPriceUSD` (added v1.8, distinct from the current-value estimate), `escrituras` (Si/No only), `esEjido` (boolean), `propEscriturado` (shown as **"Nombre Escriturado"**), `propuestaTraspaso` (legacy, no longer read/written by the app), `planLargoPlazo` (3 values), `ownershipPct`/`liensNotes`/`hoaFeeUSD`/`documentsUrl` (added v1.8), `folioReal`/`claveCatastral`/`cuentaPredial`/`usoDeSuelo`/`notario` (MX-only registry IDs, added v1.8), `pin` (USA-only), `county`/`titlePolicyInfo`/`legalDescription` (USA-only, added v1.8), `lat`/`lng` (for the map view), `aiResearchEN`/`ES`, `aiValueEstimateEN`/`ES`, `researchDate`, `archived`/`archivedReason`, `createdBy`/`createdAt`, `updatedBy`/`updatedAt`.
  - `Users` tab: `email`, `role` (`member` | `admin`), `addedBy`, `addedAt`.
  - `AuditLog` tab: `ts`, `user`, `action`, `entityType`, `entityId`, `detail` (JSON — full row snapshot for `delete_property`, since hard delete needs a recovery path).
- No secrets in Script Properties for v1 — no Gemini key, no Maps API key. There is NO live AI integration: the `aiResearch*`/`aiValueEstimate*` fields are static text, hand-authored once (see "Data & research" below), not generated at runtime.
- Google Maps links are computed **client-side only**, from address+city+state+country via `encodeURIComponent` into a plain `google.com/maps/search` URL — no API key, no geocoding, ever.

## Access control
- `roleFor_(email)`: if `Users` is empty, the first person to open the app becomes `admin` (bootstrap). Otherwise, an email not on the list gets role `'none'` — **not** a "guest" role, this is a private app, not org-open. `requireUser_()` gates all reads; `requireAdmin_()` gates admin-only writes.
- `member`: view everything, add a new property, edit any property's fields.
- `admin`: everything a member can, plus archive/unarchive/delete a property, and manage the `Users` list (add/remove/change role). Same "can't demote/remove the last admin" and "can't remove yourself" guards as the sibling app.
- Delete is a true destructive row-delete (admin-only). The client makes the admin type the property's `referencia` to confirm; the server checks it again (`deleteProperty(id, confirmReferencia)`); the full row is snapshotted into `AuditLog.detail` first, since that snapshot is the only recovery path.

## Data & research (read this before touching `SEED_PROPERTIES_`)
- `SEED_PROPERTIES_` in `Code.js` is a hand-authored array of all 41 properties (34 Mexico + 7 USA), cleaned up from the family's original Excel listing (`Mexico` and `USA` tabs only — the `Mexico Propuesta 2` and `Sheet3` tabs in that file are historical/redundant and were never migrated).
- Cleanup decisions baked into the seed data: country spelling normalized (`Mexico`/`México` → `countryCode: 'MX'`), `status` derived from the original `Observaciones` text (kept verbatim in `observacionesRaw` too), the one placeholder price (`Oficina OE Maravatio`, literally `"1"` in the source) flagged via `precioEstimadoIsPlaceholder: true` rather than treated as a real number, "Oficina Aurora"'s city corrected from "Chicago" to "Aurora, IL" to match its actual address, and the sold Chicago house ("casa Willow") pre-archived (`archived: true, status: 'vendida'`).
- `aiResearchEN/ES` and `aiValueEstimateEN/ES` were written **once**, by an AI assistant doing real web research per unique city/area (not per individual property — properties sharing a city reuse that area's research, personalized per property type/status) and are stored as plain static text. **There is no "regenerate" button and no runtime AI call anywhere in this app** — that was a deliberate v1 scope decision (Jorge: "I rather you do the research now... we won't need to update constantly"). If the research ever needs refreshing, it's a manual re-write of the relevant `SEED_PROPERTIES_` entries (or a direct edit in the underlying Sheet — the UI shows these fields read-only), not a feature to build.
- **The registry seeds itself automatically.** `ensureRegistry_()` calls `seedIntoRegistry_()` the moment the spreadsheet is first created — i.e., the very first time anyone opens the app. There is no manual "run this once from the Apps Script editor" step, because a headless `clasp`-deployed cloud session has no browser to click Run in, and `clasp run` requires the project to be set up as an API-executable (extra GCP wiring not worth doing for a one-time seed). `seedProperties_()` still exists as an admin-callable fallback, guarded by the same `SEED_DONE` Script Property, in case the registry ever needs a manual re-seed.
- **`SEED_DEFAULTS_`** supplies blank defaults for fields most rows don't need (`propietario`, `cp`, `escrituras`, `pin`, etc.) — each `SEED_PROPERTIES_` entry only needs to specify fields that differ from blank/false.

## Schema v2 migration (shipped v1.2 — read before touching status/escrituras/planLargoPlazo)
v1.2 reworked the estate-planning fields per Jorge's request: `escrituras` is Si/No only now (ejido tenure moved to its own `esEjido` boolean, since ejido land doesn't really have a conventional "deed"), `status` shrank from 9 values to exactly 4 (`en_uso`/`libre`/`en_venta`/`vendida`), and the old free-text `propuestaTraspaso` succession field was replaced by `planLargoPlazo` (exactly 3 values: `mantener_individual`/`fideicomiso`/`vender`). `propietario`/`propEscriturado` kept their column keys — only their UI labels changed ("Dueño Beneficiario"/"Nombre Escriturado") — since the original spreadsheet already tracked "who benefits" and "who's on the deed" as two different things in most rows.
- **`migrateSchemaV2_(ss)` in `Code.js`** runs from `ensureRegistry_()` on EVERY call (both the "just created" and "already existed" branches), guarded by a `SCHEMA_V2_DONE` Script Property for a cheap no-op after the first pass. The real safety net is per-row-per-field idempotency: it only rewrites a field if its current value isn't already a valid new-shape value (e.g. only remaps `status` if it's not already one of the 4 new values). This matters because a fresh install seeds directly from `SEED_PROPERTIES_` in the new shape, and a naive migration pass over already-new-shape rows would wrongly re-collapse them using the OLD-value lookup table. **If you ever touch this function, re-run `node test/all.js server` and check the "schema v2 migration" group** — it seeds a fake legacy-shaped row directly into a fake sheet and asserts both the migration and the untouched-fresh-row case.
- Legacy-value mapping rules (best-effort, not reviewed row-by-row — the original text is always preserved in `observacionesRaw` for exactly this reason, so anything guessed wrong is visible and easy to fix from the edit form): `escrituras` matching `/^s/i` → `Si`, else → `No`, with `esEjido` set from `/ejido/i`; `status`: `in_use→en_uso`, `for_sale→en_venta`, `sold→vendida`, everything else → `libre`; `planLargoPlazo`: text containing "vender" → `vender`, containing "fideicomiso" → `fideicomiso`, else → `mantener_individual`.
- `lat`/`lng` (new, for the map view) are backfilled for legacy rows by matching `referencia` against a table built from `SEED_PROPERTIES_` at runtime (single source of truth — there's no separate coordinates file to keep in sync). **As of v1.3, `lat`/`lng` are ordinary editable fields** (add/edit form, under Location) — there's still no runtime geocoding (deliberately, to avoid any paid API), but a new property starts with no pin until one is entered by hand, and any pin can be corrected directly from the app without a code change.
- Both name fields (Nombre Escriturado / Dueño Beneficiario) in the add/edit form share one `<datalist>` built from every distinct name already used across the portfolio (`nameDatalist()` in `JavaScript.html`) — pick an existing name or type a new one.
- The interactive **Map view** (`STATE.view === 'map'`) loads Leaflet from a CDN (`Index.html`'s `<link>`/`<script>` tags — `unpkg.com/leaflet@1.9.4`) and OpenStreetMap tiles at render time — no Google Maps API key, no billing, ever. `initMap()` tears down any previous map instance and re-creates it (cheap enough at ~41 markers), and applies a small deterministic jitter per marker (`jitter_()`, keyed off the property id) purely for on-screen legibility where several properties share one town-center coordinate — never stored, recomputed the same way every render. `test/client.js` verifies `initMap()`'s own logic against a **fake `window.L`** (no real network dependency in the test suite); the actual CDN/tile load is a manual-smoke-test item.

## Map pin corrections (v1.3) + automatic geocoding (v1.4)
- **The z-index bug (fixed v1.3)**: opening a property's detail modal from a map pin's popup used to render the map ON TOP of the modal instead of underneath it. Root cause: Leaflet assigns its own internal panes/controls z-index values up to 1000, and `.leaflet-container` doesn't establish its own CSS stacking context by default — so those values were compared directly against `.modal-backdrop`'s `z-index: 50` in the page's top-level stacking context, and won. **Fix: `.map-container` (the div Leaflet attaches to) has `position: relative; z-index: 1;` in `Styles.html`**, which gives it its own stacking context — everything Leaflet draws inside stays contained there (however high its internal z-index values are), and the modal correctly paints on top. **This is the pattern to reuse for any future embedded third-party widget that manages its own internal z-index stack** — contain it at the container level, don't try to out-number its internal values from outside.
- **Pins are geocoded automatically now (v1.4)** — the earlier hand-estimated coordinates (and the v1.3 `LATLNG_FIXES_V1_` spot corrections, kept for history) are superseded. **`Maps.newGeocoder()` is Apps Script's BUILT-IN geocoding service: Google's geocoder, but no API key, no billing account, no oauth scope — just a free daily quota (~1,000 lookups/day consumer, more on Workspace).** The original "no Google Maps" constraint was about keys and billing; this satisfies it. The moving parts, all in `Code.js`:
  - `geocodeOnce_(query, countryCode)` — one lookup, region-biased (`setRegion('mx'|'us')`), wrapped in try/catch so quota/service failures degrade to "no result" instead of breaking a save, and **bounds-checked against `COUNTRY_BOUNDS_`** (a result outside the property's own country is treated as a miss — the classic geocoder failure for sparse rural addresses like "El Gigante" is a confident match on the wrong continent).
  - `geocodeProperty_(p)` — full address (`direccion, ciudad, estado, cp, país`) first; on a miss, falls back to `ciudad, estado, país` (town-center precision, automatic — same as the rural parcels always had).
  - `addProperty`/`updateProperty` — a new property with blank coordinates is geocoded at save; on edit, blank coordinates → geocode, **address changed with coordinates left prefilled → re-geocode (the pin follows the address)**, coordinates the user actually typed always win.
  - `regeocodeAllV1_` — one-time pass (Script Property `GEOCODE_ALL_V1_DONE`) that re-located every existing pin from its address on the first load after the v1.4 deploy, replacing all the hand-estimates wholesale. Rows where the geocoder finds nothing keep their previous coordinates.
  - `relocateAllPins()` — admin-callable re-run of the same pass, wired to a **"Reubicar todos los pines" button in the Admin panel footer**. Use it after fixing a batch of addresses, or if the one-time pass ran while the service was unavailable.
- Manual `lat`/`lng` fields survive in the add/edit form purely as an **optional override** (the hint text says so); tests fake the `Maps` service via `__setGeocode(fn)` in `test/lib/gas-stubs.js` — the real service's behavior on this OE account is a manual-smoke-test item (if it ever throws an authorization error, saves still succeed without pins; run "Reubicar todos los pines" after resolving).

## Geocoding diagnostics (v1.5) — read this before assuming "wrong pin" means "wrong geocoder"
- **Context**: after v1.4 shipped automatic geocoding, Jorge reported pins were STILL wrong for specific properties (Edificio J.A, Edificio Corporativo, Dpto. Prairie) and asked about integrating "the real Google Maps API" — a reasonable-sounding ask that's actually a misunderstanding worth remembering: **`Maps.newGeocoder()` already calls Google's real Geocoding API**, just for free and without a key. A "direct" integration would hit the identical backend. The real fix for "pins are wrong" is almost never "swap the geocoder," it's "find out what query is being sent and what came back" — hence diagnostics before any further geocoder change.
- **`geocodeProperty_(p)` (`Code.js`) now returns a rich result**: `{ lat, lng, method: 'address'|'city'|'none', status, query, addressStatus, addressQuery }`. `addressStatus`/`addressQuery` ALWAYS reflect the address-level attempt's own outcome — even when a city-level fallback subsequently succeeds and would otherwise mask that the address attempt itself errored or matched nothing. Don't collapse these back into a single status field; that's the exact bug this shape fixes (see the "geocoder exception on the address attempt is reported even if a city fallback then succeeds" test in `test/server.js`).
- **`stripUnitNoise_(s)` (`Code.js`)** strips `Unit|Uni|Apt|Apto|Dpto|Depto|Suite|Ste` + trailing token/number from the address string before it's ever sent to the geocoder — confirmed necessary for `Dpto. Prairie` (`"1211 S. Prairie St, Unit 2201"`), a known geocoder confuser. Applied only to the address-level attempt; the city-level fallback query never had unit noise in it anyway.
- **`relocateAllPins()` returns `{ updated, kept, details: [...] }`** — `details` has one entry per property (`referencia`, `before`, `after`, plus everything from `geocodeProperty_`'s result). The Admin panel's **Pines/Pins tab** (`renderPinsTab()` in `JavaScript.html`) renders this as a table, row-tinted by outcome (a clean address-level `OK` vs. a `city`-fallback vs. a `none` failure), with the address-attempt failure surfaced as a sub-note when it's masked by a successful fallback. This is the tool to reach for FIRST any time a pin looks wrong — the exact query string sent and the geocoder's raw status answer "is this a stripped-noise problem, a genuinely bad address, or a real geocoder miss" without guessing.
- **Two Ohio St properties (Edificio J.A, Edificio Corporativo) were named as still-wrong by Jorge but could NOT be root-caused from stored data alone** — their addresses ("669 W. Ohio St"/"685 W. Ohio St.", Chicago) look clean, no unit noise, nothing obviously malformed. The diagnostics table is what will actually answer this once Jorge runs "Reubicar todos los pines" for real and can see the method/status/query the live geocoder actually returned for those two rows.

## Map pin jitter bug (v1.6) — geocoding was fine, rendering wasn't
- **This is exactly the follow-up the v1.5 diagnostics were built for.** Jorge ran the live app and the Admin → Pines table reported `Edificio Corporativo` geocoded to `41.89215, -87.64566` — which he independently confirmed against Google Maps as the CORRECT address location. But the pin on the app's own Leaflet map rendered several blocks away. That split (diagnostics say "correct", the map shows "wrong") pointed straight at the map-rendering code, not the geocoder — exactly the kind of narrowing the diagnostics table exists to make possible.
- **Root cause**: `initMap()` in `JavaScript.html` calls `jitter_(p.id)` — a small deterministic per-id offset (up to ~0.005° in each of lat/lng, ~500m) — on EVERY marker, unconditionally. It was written for one legitimate case: several rural Maravatío parcels that all fall back to the same town-center coordinate and would otherwise render as one indistinguishable stacked pin. It was never meant to touch a property with its own precise, uniquely-geocoded address — but the code didn't check for that, so it silently nudged every single pin on the map, precise ones included.
- **Fix**: `initMap()` now builds a `coordCounts` lookup (keyed by `lat.toFixed(5) + ',' + lng.toFixed(5)`) over the currently-filtered property list before placing any markers, and only applies `jitter_()` when a property's coordinate is shared by 2+ properties in view. A property with a unique coordinate now renders at EXACTLY what the geocoder returned — no nudge, ever.
- **Lesson for next time a pin looks wrong**: check the Admin → Pines diagnostics table FIRST. If it reports the coordinate you independently verify as correct, the bug is downstream in rendering (as it was here), not in geocoding — don't re-touch `geocodeProperty_`/`Maps.newGeocoder()` on a hunch when the diagnostics already show the geocode succeeded.
- `test/client.js`'s map-view suite asserts a unique-coordinate property renders at its exact `lat`/`lng` (not jitter-shifted), and a separate test group with two properties forced onto one identical coordinate asserts the jitter still applies there — so a regression toward "jitter everything again" or "jitter never applies" would both be caught.

## direccion2 + the Union St regex bug (v1.7)
- **`direccion2`** is a new ordinary field (schema, `EDITABLE_FIELDS_`, export, seed, form, detail view — same plumbing pattern as every other field) for an apartment/interior/suite number, kept separate from `direccion` on purpose. It is NEVER included in the geocoding query (`geocodeProperty_` only ever reads `direccion`/`ciudad`/`estado`/`cp`) but IS included in the human-facing "Open in Google Maps" link (`mapsLink()`/`mapsLink_()`) — Google's map search UI is forgiving of a unit number in a way the strict Geocoding API is not, so showing it there is safe and actually more useful.
- **`splitAddressUnitV1_(ss)`**, gated by `SPLIT_UNIT_V1_DONE`, is a one-time per-row-idempotent migration (same shape as `fixLatLngV1_`/`migrateSchemaV2_`) that pulls an already-embedded unit token out of a live sheet's `direccion` into `direccion2`, using `UNIT_NOISE_CAPTURE_RE_`. It only touches a row whose `direccion2` is still blank, so a value someone has since typed by hand is never overwritten. `SEED_PROPERTIES_`'s 3 rows that used to carry embedded unit noise (Departamento D.F, Dpto. Cancun, Dpto. Prairie) were rewritten to already carry the split shape, so a fresh install never needs the migration — same pattern as every prior schema addition in this app.
- **A real, previously-shipped bug was caught while writing this migration's test, not invented for it**: `UNIT_NOISE_RE_`/`UNIT_NOISE_CAPTURE_RE_` (added in v1.5) had a bare `Uni` alternative meant to catch a Spanish "Uni" abbreviation, but with no word-boundary check after it — so it matched as a PREFIX of any longer word too. Against `"22 N Union St"` (Edificio Oficina Aurora), the regex matched `Uni` and then its own greedy trailing `[\w-]*` devoured the rest of the word ("on"), stripping the entire street name and sending `"22 N St"` to the geocoder instead. **Fix: both regexes now require `\b` immediately after the keyword alternation**, before the optional trailing period/number, so a match only fires on a whole word (`Unit`, `Uni`, `Apt`, `Dpto`, etc.), never a prefix. `test/static.js`'s new seed-data check ("no seed row still has a unit/apt/interior number embedded in direccion") is what surfaced this — it flagged `Edificio Oficina Aurora` as a false positive, which traced straight back to the regex, not the address. `test/server.js` has a dedicated regression test (`geocodeProperty_` on "22 N Union St" must send a query that still contains "Union").
- **Take the lesson from v1.6 forward here too**: this Union St bug had been live since v1.5 and nobody had reported "Edificio Oficina Aurora's pin looks wrong" yet — it's very plausible that pin has been silently wrong (city-fallback level at best) this whole time. Worth Jorge checking that specific pin now that both the regex and, from v1.6, the jitter bug are fixed.
- **`render()`'s focus/caret-preservation fix** was a prerequisite for the column filters to be usable at all — a full `innerHTML` rebuild on every keystroke would otherwise blur whatever text input you're typing into after each character (this affected the pre-existing global search box too, just less noticeably since most people click back in without registering why). `render()` now saves `document.activeElement`'s id + selection range before rebuilding and restores both afterward.

## Tracking fields + dynamic form (v1.8)
- **Scope was deliberately negotiated, not assumed** — a broader proposal (lot/construction size, acquisition basis, ownership/legal extras, MX/USA registry IDs, plus a few things left OUT: multi-owner % splits as a real data model, mortgage tracking, insurance policies) was narrowed down by asking which categories actually mattered before writing any code. `ownershipPct` is a deliberate simplification: a single optional number (blank = assume 100%/sole owner), NOT a real multi-owner list with named co-owners — flagged explicitly as a scope call, revisit if that's ever actually needed.
- **New fields, all plain optional columns** (schema, `EDITABLE_FIELDS_`, `SEED_DEFAULTS_`, `listProperties()`, `addProperty()`, `EXPORT_HEADERS_` — same plumbing pattern as every prior field addition): `lotSizeValue`/`lotSizeUnit`, `constructionSizeValue`/`constructionSizeUnit`, `acquisitionDate`/`acquisitionPriceUSD`, `ownershipPct`, `liensNotes`, `hoaFeeUSD`, `documentsUrl`, and the MX-only (`folioReal`, `claveCatastral`, `cuentaPredial`, `usoDeSuelo`, `notario`) / USA-only (`county`, `titlePolicyInfo`, `legalDescription`) registry IDs.
- **`addTrackingFieldsV1_(ss)`**, gated by `TRACKING_FIELDS_V1_DONE`, is the retrofit for a LIVE sheet created before these columns existed — unlike `migrateSchemaV2_`, there's no value-remapping here at all, just making sure the header row has every new column name, via the pre-existing `ensureColumn_` helper (itself idempotent). A fresh install already has every column from `PROPERTIES_HEADERS_` at creation time, so this is a no-op there. `test/server.js` exercises the REAL retrofit path (not just the trivial fresh-install case) by deliberately truncating a fake sheet's headers — and rebuilding every row's cell values to match, since a plain header filter alone would misalign existing data — back to a pre-v1.8 shape before re-bootstrapping.
- **Size units are per-property, not forced by country**: `lotSizeUnit`/`constructionSizeUnit` are free dropdowns (m², hectares, sq ft, acres — construction is restricted to m²/sq ft only, since a building footprint is never in hectares) defaulting to whatever's conventional for the property's country (`defaultSizeUnit_()`) but always overridable, so a rural Mexican parcel recorded in hectares doesn't need converting to match a MX default of m².
- **The add/edit form reacts live to Tipo and Country now** (`MPT.reflowForm(key, val)`, wired via `onchange` on both selects) — it reads back everything already typed via `readForm()`, merges in the new key/value, and re-renders `STATE.modal.prop` from that merged object, so switching either dropdown mid-edit never loses other fields. This is what makes `tipoNeedsLot_()`/`tipoNeedsConstruction_()` (hide construction size for `Terreno`, hide lot size for `Departamento`) and the whole MX-vs-USA registry section swap actually usable while filling out the form, not just on next reopen.
- **A real, pre-existing bug got fixed as a side effect of building this**: the add/edit form's "USA — Parcel" group used to render **unconditionally**, regardless of the selected country — visible directly in a screenshot of a Mexican property's edit form showing an irrelevant Parcel PIN field. The read-only detail view had always correctly gated this on `p.countryCode === 'US'`; the form never did. Now both the form and detail view branch the same way, and the country-swap logic (`country === 'US' ? ... : ...`) makes a THIRD state (neither MX nor USA fields) impossible by construction — one of the two always renders.
- **`documentsUrl` gets an XSS guard, not just an `esc()` call**: it's free-typed by any authorized member (not just admin), then rendered as a clickable `<a href>`. `esc()` alone only HTML-escapes the string for the attribute context — it does NOT stop a `javascript:...` URI scheme from executing when clicked. `safeUrl_()` allowlists `http://`/`https://` only; anything else (including a bare `javascript:` payload) renders as no link at all rather than a live one. `test/client.js` has a dedicated regression pair (`https://...` renders as a link; `javascript:alert(1)` does not).

## Deploy workflow
- **Single deployment, no dev/exec two-tier ceremony** (unlike the sibling CL app) — this is a small family tool with a handful of users, not a team product where protecting a shared URL from an in-progress push matters. One deployment id, reused via `clasp deploy -i "$WEBAPP_DEPLOYMENT_ID" -V <version> -d "description"`.
- `./clasp-push.sh` pushes the current working tree to `@HEAD` and byte-verifies the push landed (`clasp_verify_push` — see the sibling CL app's CLAUDE.md for the 2026-08-06 incident this defends against: a push can print "Pushed N files" and exit 0 while the deployed script stays stale).
- To actually ship a change to the live `/exec` URL after pushing to `@HEAD`:
  ```
  clasp -A .clasprc.json create-version "description of the change"   # prints "Created version N"
  clasp -A .clasprc.json deploy -i "$WEBAPP_DEPLOYMENT_ID" -V N -d "description of the change"
  ```
  Note clasp v3's `create-version` takes the description **positionally**, not via `-d` (that flag is silently wrong on `create-version`, though correct on `deploy`) — same trap documented in the sibling repo.
- `clasp-env.sh` (sourced by `clasp-push.sh`) restores `.clasprc.json` from `CLASP_AUTH_OE_B64` if it's missing, finds clasp without requiring a global install, and refuses to run outside this repo's directory. Always pass `-A .clasprc.json` explicitly on every clasp command in a cloud session — bare `clasp` looks for a global `~/.clasprc.json` that doesn't exist there.
- `CLASP_AUTH_OE_B64` was already present in this environment when this project was built (proven working for several other OE-account repos: `oe-monitoring-app`, `oepm-trackerbot`, `oe-jcarlos-app`, `loft-dashboard-appscript`) — no separate auth setup was needed.
- Rollback: `clasp -A .clasprc.json deploy -i "$WEBAPP_DEPLOYMENT_ID" -V <older version> -d "rollback to vX"` — versions are immutable, so old ones are always still there.

## Apps Script gotchas (same class of bug as the sibling repo — read before editing served files)
- **Comment-stripping**: HtmlService's sanitizer can corrupt a `/* */` sequence even where it isn't a real comment (e.g. inside a string literal like `accept='image/*'`). The safest rule, followed throughout this repo: **`Index.html`, `Styles.html`, and `JavaScript.html` contain the two-character sequence `/*` or `*/` NOWHERE at all** — not even in legitimate CSS section comments. `test/static.js` enforces this with a whole-file scan (stricter than the sibling repo's suite, which only checks the served `<script>` block and exempts `Styles.html` — that exemption may be correct per that repo's own test comment, but this repo doesn't rely on it either way). `Code.js` is NOT served through HtmlService and can use normal `/* */` comments freely.
- **Load-order**: never read data at top level in `JavaScript.html`. The client calls `getBootstrap()` on load and computes everything inside that success handler.
- **Single spreadsheet, execution-scoped cache**: `CACHE_` in `Code.js` avoids re-opening the registry spreadsheet multiple times within one execution (Apps Script rebuilds globals fresh on every invocation, so this cache can never go stale ACROSS requests — only kills repeated `openById` calls WITHIN one). `bustReg_()` clears it after any write.
- **`ensureRegistry_()` recursion trap**: `seedIntoRegistry_()` is called from inside `ensureRegistry_()`, before `CACHE_.ss` is set — it must never call `ss_()`/`audit_()` (which would call `ensureRegistry_()` again and create a second spreadsheet). It writes directly to the `ss` object it's passed instead. Keep this in mind if `seedIntoRegistry_()` or `ensureRegistry_()` is ever refactored.

## Setup on a new machine / session (clone-based)
1. Clone: `git clone https://github.com/jmiranda7891/miranda-property-tracker.git`
2. `npm install` (installs Playwright for the `client` test suite only — nothing here is deployed to Apps Script; `.claspignore` is the whitelist that enforces that).
3. In a cloud session, `CLASP_AUTH_OE_B64` should already be present in the environment; `clasp-env.sh` restores `.clasprc.json` from it automatically on the first `./clasp-push.sh` run.
4. `npm test` before any push — it's fast (~3s) and it's what would catch a broken deploy before Apps Script does.
5. `./clasp-push.sh` to push to `@HEAD`; see "Deploy workflow" above to actually move the live `/exec` URL to a new version.
6. Nothing secret to provision — the registry spreadsheet is created automatically (and seeds itself) the first time an authorized user opens the app. Do not manually create a "Miranda Family - Property Registry" spreadsheet — that would race with the app's own `ensureRegistry_()` and potentially produce a duplicate.
